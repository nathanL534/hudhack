# Bloat Check: Stage-6 Primary Metric Diff

## Finding 1 — KOTH_BOUNDS duplicated verbatim across two files

`output/stage6/koth_cross_game.py:48-53` defines `KOTH_BOUNDS` as a module-level dict with the exact same four keys and values as `output/stage6/games.py:163-168` (`KOTH_BOUNDS: dict[str, tuple[float, float]]`). `koth_cross_game.py` already imports from `output.stage6.games` for `get_game`; it could just import `KOTH_BOUNDS` from there. The `map_fighter_arena_to_koth` function in `koth_cross_game.py` even inlines a second manual clamp on `platform_width` (line 66) using the local dict instead of calling its own `_clamp` helper for consistency. With two authoritative sources the bounds can silently drift — if someone tightens the `zone_half` floor in `games.py`, `koth_cross_game.py` silently uses the old value for the cross-game mapping test. Fix: import `KOTH_BOUNDS` from `output.stage6.games` in `koth_cross_game.py` and delete the local copy.

## Finding 2 — `local_train_student_worker` / `local_head_to_head_worker` are trivial one-liner aliases that add an indirection layer without reducing anything

`modal_player.py:798-805` adds two public functions that are single-line pass-throughs to the private implementations immediately above them: `local_train_student_worker` calls `_train_student_policy(payload, seed)` and `local_head_to_head_worker` calls `_head_to_head_match(payload, seed)`. The only consumers of these names are the `if backend == "local"` branches in `output/stage6/head_to_head.py:121-136`, which import them by name from `modal_player`. There is no reason the private functions cannot be imported directly, or the local dispatch could call `_train_student_policy` / `_head_to_head_match` via a thin import of the module itself. As written, navigating "which function does the local path actually run" requires two hops with no gain. The docstrings ("Credential-free local fallback: ..., no Modal") add prose that is already obvious from context. Either make the privates importable by renaming them (drop the underscore) or have the `head_to_head.py` dispatch call them directly.

## Finding 3 — `_model_of` in `modal_player.py` is a single-call helper that adds a hop with no reuse

`modal_player.py:642-650` defines `_model_of(job)` — a 6-line function that calls `getattr(job, "model", None)` and raises `AttributeError` with a message if it is None. It is called exactly once, at line 543 inside `_train_student_policy`. The error message ("training job does not expose the SB3 model") is legitimately useful, but it does not require its own named function — inline the `getattr` + guard at the call site (3 lines) and the message can live right there. As a separate named function it creates a false expectation of reuse that never materialises across this diff.

## Finding 4 — `koth_trainer.py` duplicates `ppo_trainer.py` at the class/method level when a parameterised base would suffice

`harness/koth_trainer.py` is an acknowledged structural twin of `harness/ppo_trainer.py`. Looking at the two side by side: `_set_global_seeds`, `_curriculum_id_of`, `_make_policy_from_model`, and the `_winrate` loop body (lines 455-461 of koth_trainer vs lines 220-229 of ppo_trainer) are identical modulo the type annotation on the arena parameter. The `_MultiArenaKothEnv` and `_MultiArenaFighterEnv` classes differ only in the inner env class they instantiate (`KothEnv` vs `FighterEnv`) and the opponent factory call — their `__init__`, `reset`, `step`, and `close` implementations are structurally line-for-line copies. The `_PPOTrainingJob` / `_KothTrainingJob` classes are identical. The docstring justification ("deliberately does NOT touch ppo_trainer.py — frozen") is valid for avoiding regressions but does not justify the full duplication: a single generic `_MultiArenaEnv(env_cls, opponent_factory, arenas, seed)` would eliminate the env-class duplication without touching the existing fighter path. The PPO hyperparameters are intentionally identical, which is the correct design — but identical hyperparameters is an argument for a shared config constant, not a second copy. The duplication is ~120 lines of structurally identical code. If `koth_trainer.py` drifts from `ppo_trainer.py` on a PPO hyperparameter (e.g. n_steps changes for the fighter), the KOTH trainer silently uses the stale value, making the "identical architecture" fairness claim false.

## Finding 5 — `validate_replay` return value is inverted in `_capture_h2h_replays`, silently discarding all replays

`modal_player.py:762-763` (inside the nested `_roll` function in `_capture_h2h_replays`): `if validate_replay(data): return None, sim.winner`. `validate_replay` (defined in `replay.py:141`) returns a **list of problems** — an empty list means the replay is well-formed. The code discards the replay (`return None`) when the problems list is **truthy** (i.e. when there ARE problems), and propagates it when the list is falsy (empty = valid). So far so good. But the control flow at line 769 is `if data_a is None: continue` — meaning it skips the match-seed when `data_a is None`, which happens when there ARE validation problems. That part is correct. However, this means a structurally invalid replay is silently swallowed and no problem list is logged or surfaced anywhere — the caller just sees `None` and moves on. This is not wrong in the "replays are best-effort, never gates" sense that the comment at line 724 documents, but it is a silent error swallow with no diagnostic: if the ReplayBuilder produces consistently malformed output the dashboard's replay player will show nothing and there is no log line to debug from. This is medium-severity because replays are optional, but it is the one place in the new code where a real failure is completely silent.
